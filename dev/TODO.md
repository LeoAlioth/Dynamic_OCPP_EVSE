## Backlog

- [ ] **Off-grid: generator on the grid CT** — an off-grid site may run a backup generator wired through the "grid CT" input. The engine currently equates "has grid CTs" with "grid-tied" (`site.is_off_grid = not has_grid_cts` in `run_hub_calculation`), so a generator-backed site would be treated as having an unlimited utility feed behind the main breaker. Needs a CT/site type setting (grid vs generator): cap the "grid" pool at the generator's rating instead of the main breaker, and disable export-based logic (solar surplus from export, Excess mode) since a generator cannot absorb export.
- [ ] **Entity-backed inverter capacity** — the inverter max power (`CONF_INVERTER_MAX_POWER`) is a fixed value set at config time. Add an optional entity override, mirroring the Max Import Power slider + `CONF_MAX_IMPORT_POWER_ENTITY_ID` pattern: when an entity is configured, `run_hub_calculation` reads its live value each cycle. This lets an external automation drop the inverter capacity toward 0 on an inverter high-temperature alarm — a clean replacement for a per-load inverter-overheat failsafe (cf. the `evse.yaml` controller's stop-on-overheat) without a dedicated emergency-stop input.
- [ ] **Device-based OCPP discovery (refactor)** — discovery already works and auto-finds per-phase L1/L2/L3 entities, but by _guessing_ sibling entity names from a `base_name` prefix (`_discover_ocpp_chargers` in `config_flow.py`), and the OCPP device ID is a free-text field. Replace with a device-registry **device selector** + enumerate entities via `entity.device_id`, so it's robust to non-standard OCPP entity naming and supports per-phase separate entities reliably.
- [ ] **`excess_margin`: unify the two sinks (refactor)** — `excess_margin` in `calculations/target_calculator.py` branches on `site.is_off_grid` twice, which makes on-grid and off-grid read like two different rules when they are one rule applied to two sinks: _a sink contributes its allowance only while it exists and can absorb_. The grid sink exists when CTs are configured (capacity effectively unlimited, allowance = `excess_export_threshold`); the battery sink exists when configured and can absorb until `battery_soc_full` (allowance = `battery_max_charge_power`). Restructure as a symmetric pair — each sink contributing (currently placed, allowance) and both summed — so the code states that rule and a third sink (second battery, heat store, V2G) becomes an append rather than another branch. Separately, the second `is_off_grid` check (the managed-draw add-back) is not about sinks at all: it exists because `_apply_feedback_loop` already restores managed draws into the grid reading on-grid and returns early off-grid. Name it after that cause — e.g. `_apply_feedback_loop` sets `site.draws_restored_in_export`, and the margin restores them only when it hasn't happened — so the dependency is explicit and can't break silently if the feedback loop's early-return conditions change. **Not pursued:** the branchless form `absorbed = solar_production_total - household_consumption_total` (algebraically what both paths compute, _P − H_) trades two direct sensor readings for two derived values, and `household_consumption_total` is `None` unless a dedicated solar sensor is configured. Behavior-preserving, so `dev/tests/test_excess_margin.py` + the scenario suite are the check. `is_off_grid` stays in the codebase either way (zero grid headroom, feedback-loop skip).
- [x] **Inverter write-control** — DONE (charge-rate half): an inverter entry can name its charge-limit `number` register, and `control/inverter.py` writes the forecast's recommended limit to it behind an opt-in **Battery Charge Control** switch, with a min-interval + deadband and a write-once release to the normal value. Max-SOC write support was deliberately not built: on Deye the ceiling is expressed as TOU slots rather than a register, and slowing the fill is the gentler control. Revisit if an inverter with a real max-charge-SOC register turns up.
- [x] **Slim the hub flows post-import** — DONE: new hubs skip the inverter page and are flagged imported from birth; reconfigure/options hide the inverter page and keep only hub-scoped battery fields once imported. Legacy pages remain only while un-imported legacy fields exist.
- [ ] **EMA warm-up on auto-import** — the imported inverter entry uses fresh per-entry EMA keys, so smoothing restarts cold once at migration (~10 s at the default 2 s cycle). Harmless; seed from the legacy `inv_{i}`/`battery_power` keys if it ever matters.
- [ ] **Forecast-driven load pre-run** — use the PV clipping forecast the other way around: start Excess-capable loads (tank boost, power station, plug) *before* the clipping window when `forecast_clipped_kwh − forecast_absorbable_kwh > 0` predicts unavoidable curtailment, so the surplus goes into hot water / the station instead of being curtailed. Deferred from the forecast feature — needs per-load energy-to-absorb estimates and a scheduling notion the engine currently doesn't have.
- [ ] **SG Ready device type** — 2-relay site-state mapping (Block/Normal/Recommend ON/Force ON), no user modes
- [ ] **Rename generic `charger` → `load`** _(low priority)_ — `charger` is used as the generic term for a managed device, but plugs and hot water tanks aren't chargers (the codebase already uses `LoadContext` / `LoadJuggler`). Large: ~3000 occurrences across ~50 files. Rename the **generic** uses → `load`: the `chargers` collections, `LoadContext.charger_id`, `SiteContext.chargers`, the `charger_*` hub-data keys (`charger_targets`, `charger_available`, `charger_modes`, `charger_rank`, `charger_draw`, `charger_names`, `charger_active_phases`, `charger_phase_masks`), the `hass.data[DOMAIN]` keys (`chargers`, `charger_allocations`, `charger_ranks`, `charger_status`), `ChargerEntityMixin` + `_write_to_charger_data`, engine funcs (`calculate_all_charger_targets`, `_sort_chargers`, `_add_chargers_to_site`, `get_chargers_for_hub`, `get_hub_for_charger`), `ENTRY_TYPE_CHARGER`, `CONF_CHARGER_ID` / `CONF_CHARGER_PRIORITY`. Renaming the stored config strings (`entry_type` value `"charger"`, `charger_priority`, `charger_id`) needs an `async_migrate_entry` bump, with the ~25 scenario YAMLs (`chargers:` / `charger_N` keys), 11 pytest fixtures, `strings.json` and both translations updated in lockstep. **Open decision when picked up:** whether to also rename genuinely EVSE-specific names (`_build_evse_charger`, OCPP `discover_chargers`, `CONF_CHARGER_L*_PHASE`, config-flow `charger_info`/`charger_current`/`charger_timing` steps, `validate_charger_settings`) or keep them — an EVSE genuinely _is_ a charger.
