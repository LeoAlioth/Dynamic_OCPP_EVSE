## Remaining from the code review (2026-08-17)

Full-codebase review (four parallel reviewers: engine/calculations, config flow/setup, entities/control, architecture/tests). 24 of the 29 findings were fixed the same day, and the design-question pass closed #41 — the flap's real cause was an **incomplete load-off reconstruction** in `excess_margin` (the hysteresis band was never the right lever: the error scales as draw ÷ phases), fixed while preserving gross per-phase export semantics; the Excess hysteresis is now a hub setting. See `RELEASE_NOTES.md` (2.0.6) for user-facing items and `git log` for the rest. Structural refactorings live in `TODO.md`. Still open:

31. **Unavailability/staleness detection re-implemented ~5× with drifting predicates** — `_read_entity` (includes `None`/`""`), the grid-stale block (adds non-finite), `_check_entity_availability` (omits `None`), station status (omits `""`), `forecast_reader.py`. `_read_grid_phases` coerces `_UNAVAILABLE` to 0 A and relies on the downstream stale block to repair it — an unrepaired 0 A grid reading grants full breaker headroom. One `is_unavailable(state)` helper should own the predicate (folds into the hub_calculation decomposition TODO).

32. **Entity layer: deprecated sensor API, no `available` handling, `None` → `0.0`** — sensors override `state`/`unit_of_measurement`/`device_class` instead of `native_value`/`_attr_native_*`, smuggle `state_class` through `extra_state_attributes` (inconsistently — some W/A sensors get long-term statistics, some don't), no hass.data-fed sensor implements `available` (values freeze silently when the producer stops), and `LoadJugglerHubSensor.state` maps `None` → `0.0` (Site Remaining Power reads 0 W on failure instead of unknown). Mechanical but wide fix → tracked as the entity-modernization TODO.

43. **Dead code, remainder** — `run_tests.py` default `yaml_file` points at a nonexistent file (harmless; the CLI always passes the scenarios dir).

48. **Display headroom uses post-feedback derived solar** *(found 2026-08-17 during the #17 dual-gate work; display-only)* — `_build_hub_result` calls `fleet.output_power_total` with post-feedback solar; on a derived-solar battery site the feedback loop folds managed draws back into the derived figure, inflating the estimated inverter output by exactly the running loads' draw and **understating Site Remaining Power** while a managed load runs. The #17 gate deliberately reads the pre-feedback figures (`inverter_output_total` / `net_grid_power` on SiteContext) — feed those same captured values into the display path.

47. **Excess margin over-credits in two stay-on cases** *(pre-existing; surfaced 2026-08-17 during the #41 latch rework, deliberately left)* — (a) grid-tied curtailment (battery full, export pinned at the limit): an engaged load's margin reads ~its own draw too high, which also inflates the excess *pool* other Excess loads see; (b) a load that pushes the battery from charging into discharging is credited via the export fold-back without the discharge being subtracted, so it stays on while the battery drains toward its floor. Both err in the stay-on direction — consistent with the accepted #17/latch stance (stability over purity, SOC floors as the backstop). Revisit only if pool inflation visibly misallocates on a real site.
